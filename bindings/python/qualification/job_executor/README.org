#+title: Python job-executor qualification case

This case belongs to the production =bindings/python= uv project. Its worker
is a real child process, its task ledger and provider effect log are SQLite
files, and the effect provider is a loopback HTTP server. The service commits
once, withholds the first acknowledgement, and lets a restarted worker retry.

The =buggy= strategy generates a new provider idempotency key after restart:
the test must fail with two commits. The =fixed= strategy retains a key derived
from the logical operation: the same test must pass with one commit and a
completed task. This is a deliberate known-fault replay, not a novel bug.

The installed-wheel project test copies the scenario outside the checkout,
installs the built wheel and locked dependencies in a new uv environment, and
runs both strategies through =lambda_aitia.verification.run_pytest=. It also
changes one source file after the passing observation and requires that
=source_current= reject the old observation. The observation is not a Scheme
Host admission. Pytest runs from captured source bytes in a fresh directory,
but repository provenance, Scheme Host admission, independent provider trust,
and a Runtime effect gate remain open.

The case challenges the original guarantee's *per key* scope: a provider can
honor that scope while a logical operation is duplicated with two keys.
[[file:../../../../docs/adrs/0008-stable-operation-key-after-lost-ack.org][ADR 0008]]
proposes a revised logical-operation guarantee and keeps its acceptance and
re-verification separate from this test result.

* Coverage boundary

The worker has one fixed job and constant payload; the provider's single SQLite
row represents both the deduplication key and the effect. This is not a model
of multi-tenant identity, changed intent, retention expiry, concurrent attempts
or atomicity across a ledger and an independent external service. Fixed mode
repairs the injected identity fault, not every idempotency failure mode.

ADR 0008's r2 coverage matrix assigns those remaining qualifications to their
owners. Existing POO Flow Cedar authorization and Runtime effect mechanisms
must be reused, not reimplemented in this fixture. A Cedar permit answers an
authorization question; it does not establish provider commit uniqueness or
resolve an unknown outcome after a lost acknowledgement.

* Focused replay receipt — 2026-09-24

The unchanged worker/test sources at Aitia commit
=f3438241780e863db6c0b518d86628b540f96cd1= were rerun during the ADR r2 audit.
From =bindings/python=, =uv run --locked --no-sync= ran
=pytest qualification/job_executor/test_unique_effect.py= with a process-scoped
=AITIA_QUALIFICATION_MODE=:

- =fixed=: one test passed; one commit and task completion were asserted.
- =buggy=: the expected negative test failed specifically at =committed == 1=,
  observing two commits, rather than failing to start the worker/provider.

This was a focused source-fixture replay in the existing uv environment, not a
new installed-wheel qualification or Cedar/Runtime execution receipt. The new
owner matrix does not promote untested boundaries to passing evidence.
