#+title: Lambda Aitia — causal assurance across the software lifecycle
#+startup: overview

* Purpose

Lambda Aitia organizes software engineering around the complete SDLC:
requirements, design, algorithms and implementation strategies, verification
and testing, delivery, operation, maintenance and retirement. Causal Assurance
connects the justification of engineering decisions across that lifecycle.
POO Flow supplies the reusable composition, temporal/causal and runtime
mechanisms. Aitia also owns the software Architecture Decision Record (ADR)
module migrated from Lambda Episteme. It answers five questions about an
engineering conclusion:

1. What exactly is claimed?
2. Which sources, assumptions, arguments and evidence support it?
3. Which structural, temporal and causal relations justify that support?
4. Which changes make the conclusion stale, unknown, conflicted or invalid?
5. Which decisions and real effects must remain blocked until the resulting
   obligations are discharged again?

The project helps form, compare and revise design decisions, then retains the
evidence explaining why their guarantees remain applicable. Requirements lead
to explicit assumptions, design alternatives, responsibilities, state ownership
and conditional guarantees. Algorithm choices and code implement those
decisions; tests and runtime observations can challenge them and reopen design.

System behavior trajectories and design/assurance evolution trajectories are
linked through evidence. Observed executions, model traces, hypotheses and
counterfactual alternatives preserve their distinct scope. Temporal order and
graph reachability alone cannot establish a causal explanation.
[[file:docs/rfcs/0004-sdlc-design-and-causal-trajectories.org][RFC 0004]] defines this lifecycle design and its pending acceptance gates.

This is a conceptual flow, not permission to collapse repository ownership.
POO Flow core never imports a concrete Lambda contribution.  Lambda Aitia may
consume the complete reviewed POO Flow public mechanism library needed by its
Software/SDLC implementation; dependency minimization is not an architectural
goal.  Applications own the explicit composition of Episteme, Aitia and POO
Flow.  Mounting this Git
submodule does not import a module, activate a Profile, run a verifier, grant a
capability, authorize a decision or execute an effect.

The production Aitia Python Runtime is maintained entirely under
=bindings/python= in this repository; it is not an example.  POO Flow's
=packages/python-runtime= remains the generic graph execution and lifecycle
mechanism and does not own Aitia semantics.  Aitia Scheme is compiled AOT
behind an owned-byte C ABI.  The Python project validates typed lifecycle
receipts and exposes them to downstream systems without reimplementing Scheme
decisions. The Python Runtime serves Aitia capabilities throughout the SDLC;
the existing =SdlcRuntime.plan()= is one implemented assurance-flow projection.
AnyIO is declared as its runtime-wide concurrency foundation; async execution
and Host admission remain separate implementation gates. Generic Graph/DAG and
FunFlow execution mechanisms remain owned by POO Flow. MRR relation-query and
lineage integration is a later design direction, outside the current Python
implementation stage.

* Core model

The initial semantic vocabulary is deliberately small:

=Artifact=, =Claim=, =Assumption=, =Observation=, =Event=, =Action=,
=Obligation=, =Evidence=, =Counterexample=, =Finding=, =Decision= and =Effect=.

Relations are typed by plane.  A generic =edge(from, to)= is not part of the
public model.

| Plane | Representative relations | Meaning |
|-------+--------------------------+---------|
| Provenance | derived-from, generated-by, cites, used | where a value came from |
| Structural dependency | depends-on, implements, tests, refines | what a change may affect |
| Temporal and causal | precedes, causal-parent, enables, prevents | what happened and why |
| Assurance | supports, discharges, defeats, invalidates | why a claim is or is not justified |
| Authority | authorizes, denies, requires-review | whether a decision may cross an effect boundary |

The planes have different admission and inference rules.  In particular,
=derived-from= is not =caused-by=, temporal order is not causal proof,
structural reachability is not assurance closure, and evidence is not action
authority.

* First executable slice

The first vertical slice is one fail-closed lifecycle:

#+begin_export mermaid
flowchart TD
    C["Source revision<br/>changed"] --> I["Structural impact<br/>affected assumptions and claims identified"]
    I --> S["Dependent support<br/>stale"]
    S --> O["New obligations<br/>pending"]
    S --> D["Old decision<br/>invalid for the changed closure"]
    D --> E["Associated effect<br/>blocked"]
#+end_export

The slice succeeds only when receipts bind the subject, source revision,
assumption set, claim, obligation, producer identity, tool identity, artifact
digest and validity interval.  Missing or conflicting facts remain explicit;
they are never converted into an inferred success.

* Agent RFC threat model and formal assurance stack

Lambda Aitia treats an Agent RFC as an executable assurance subject, not just a
design document.  The RFC states intended behavior and trust boundaries; ADRs
close bounded choices; Aitia projects their claims, assumptions, dependencies,
threats, obligations and evidence into a revision-bound Assurance Graph.  POO
Flow supplies the reusable Governance, Graph/Impact Graph, Temporal Causality,
verification-adapter, authorization-provider and Runtime mechanisms used to
evaluate that model.

** Thirty-second compression

Aitia uses existing verification methods to help choose and revise software
designs throughout the SDLC. It connects requirements, assumptions, guarantees,
RFC/ADR decisions, implementation strategies and observed behavior. A new
finding can change the design, invalidate earlier support and create new
obligations with an explanation path.

Specula already derives and validates TLA+ models, reproduces bugs and supports
incremental verification. Aitia should reuse applicable tools, models, harnesses
and checks while evaluating its own contribution: better-founded design choices,
composition obligations and traceable changes in engineering justification.
The full Specula application is optional; an upstream component or script can
be reused without handing it ownership of Aitia's lifecycle.

The comparison is about responsibility rather than feature count.  Aitia's
distinctive unit is the current, revision-bound justification of a conclusion
and its invalidation trajectory across the whole SDLC.  Its value is the
composition of specialized evidence with explicit unknown and authority
boundaries, not a new theorem prover, model checker, policy engine or Graph
implementation.

The threat model covers failures that ordinary pass/fail CI cannot distinguish:

- stale evidence is replayed after source, policy, assumption or tool changes;
- a cached Agent decision survives invalidation or revocation;
- an RFC claim, Lean statement, TLA+ model and Cedar policy refer to different
  revisions of the supposed same subject;
- tool exit success is admitted without exact input, environment and artifact
  bindings;
- a counterfactual or hypothesized trajectory is promoted into observed
  history;
- composition of independently valid components is assumed safe without a new
  composition obligation;
- an authorized intent is amplified, substituted or executed through an
  out-of-band Runtime path;
- an effect begins after revocation or is reported complete without an
  execution receipt.

No single formalism closes all of those threats.  The layers have deliberately
different propositions and trusted boundaries:

| Layer | Owns | Does not prove |
|-------+------+----------------|
| Agent RFC and ADR | intent, vocabulary, trust boundary, decisions and required obligations | that an implementation, policy or runtime matches the documents |
| Aitia Assurance Graph | exact subject/revision bindings, typed support, invalidation, unresolved frontier and verification plan | temporal safety, authorization or effect execution |
| Lean | general laws such as freshness, monotone invalidation, modality preservation, no stale authority and composition obligations | that the current deployment supplied fresh facts or executed an effect |
| TLA+/TLC | bounded lifecycle transitions and adverse interleavings across change, invalidate, plan, verify, admit, decide, authorize and effect | universal theorem proof or production authorization |
| TLAPS | mechanical checking of TLA+ proof obligations under explicit statements and trusted dependencies | implementation correspondence or production authorization |
| Cedar | an allow/deny decision for one identity-bound principal, action, resource, context, policy and entity snapshot | evidence freshness, proof construction, runtime conformance or external success |
| Runtime Host | one bounded execution attempt and its typed execution receipt | that missing proof or authorization may be inferred |

The intended evidence workflow names semantic states, not implementation
completion. RFC 0004 contains the full SDLC workflow and its design feedback.

flowchart TD
    D["RFC / ADR and sources<br/>declared"] --> S["Snapshot / impact graph<br/>bound"]
    S --> O["Verification obligations<br/>pending"]
    O --> V["Proof, model check, test / replay<br/>candidate results"]
    V --> A{"Trusted admission valid?"}
    A -->|yes| C["Scoped support<br/>admitted and current"]
    C --> G{"Effect gate allows?"}
    G -->|yes| X["Bounded Runtime attempt<br/>authorized"]
    X --> R["Receipt and observations<br/>outcome recorded"]
    R --> F["Lifecycle reassessment<br/>design review when challenged"]
    F --> D
    A -->|no / unknown| U["Unresolved / rejected<br/>affected effect blocked"]
    U --> O
    G -->|no / unknown| B["Effect blocked<br/>review / revalidation required"]
    B --> O
    C -->|changed / expired| B
#+end_export

Admission checks the subject, revision and cut. The effect gate requires a
current decision, Cedar authorization and Runtime enforcement. Every arrow is
digest- and revision-bound. Lean cannot replace Cedar, Cedar
cannot replace TLA+, a TLC completion cannot replace runtime evidence, and a
Runtime success cannot retroactively prove the RFC.  Unknown, conflicted,
stale, mismatched or unavailable inputs fail closed and remain visible in the
receipt graph.

The current repository has executable snapshot/invalidation, pure planning,
modular Lean laws, a bounded TLA+ lifecycle model and known-fault Python replay.
The connected design/trajectory experiment, upstream Recipe qualification,
Python-to-Host evidence admission and Runtime effect gate remain open. See
[[file:ROADMAP.org][ROADMAP]] for phase-specific evidence and limits.

* Project rules

- Public extension APIs are POO-native. The maintained =aitia= Case now uses
  POO Flow's =user-composition=, =compose profiles= and =use-module=.
  The former no-import =aitia.ss= convenience is an open RFC 0003 UX gate,
  not a supported loader in the current Profile algebra. Advanced overrides
  use POO slots; neither path introduces an alist or patch-language DSL.
- Functional transformations are values first.  Side effects live behind an
  explicit POO Flow verifier or runtime handoff.
- Native Scheme tests are never heap-unbounded: the Aitia Testing Interface
  defaults to 512 MiB, while complete NASA catalog and prepared-source-graph
  tests declare a bounded 2 GiB POO memory profile. POO Flow's outer test
  launcher enforces the 512 MiB pre-import boundary before this profile loads.
- Relation planes remain disjoint and fail closed at their boundaries.
- =supported=, =violated=, =unknown=, =stale=, =conflicted=,
  =hypothesized=, =counterfactual= and =not-applicable= are first-class states.
- A plan is not an execution, a receipt is not proof, proof is not current
  authority, and authority is not proof that an effect completed.
- Lambda Aitia owns Software Engineering/SDLC, NASA and GitOps source modules;
  its assurance kernel reasons over those declared facts without embedding a
  NASA- or provider-specific rule.
- Lambda Episteme retains non-SDLC vertical knowledge such as Healthcare and
  the independently owned decision-kind/ontology surfaces.
