* Objective and scope

Implement the three-layer design in [[file:../rfcs/0006-engineering-runtime-and-library-boundaries.org][RFC 0006]] through the current Yuanxu Module
framework. AITIA uses Rust for engineering execution, DE supplies extensible
engineering definitions, and user Projects select by language and problem.
This plan records implementation obligations; unchecked rows are not capability
claims. The active chat Goal owns continuation, not an automatic execution grant
from this document.

Only Aitia-owned implementation/consumers are migrated. Preserve unrelated
staged and unstaged work. Do not change Core loading semantics to accommodate
Aitia, enlarge budgets, introduce an alternate package loader, delete old Memory,
or infer authority from hypothetical model fit. No commit or push is included.

* Current source audit

Lab's =init.ss= selects Modules using =yuanxu!= and publishes configured scopes
under =init.exports=. AITIA uses its own =init.ss= for both publication and
build selection. =build.ss= consumes that declaration's =std-make-spec= with
explicit requested roots.

The initial Aitia source had ordinary reexport Interfaces, older Profile
selection, a manual build-root list and =proof/=. Proof relocation and the
first managed Modules are implemented. The independent package init
selects Assurance, ADR, formal methods, GitOps, the NASA catalog and
SDLC, together with the maintained Profiles and Scenarios. The Rust
workspace and Maturin wheel are the maintained delivery paths.
Verification assets live under =dev/=, including the relocated source
admission preflight. The current worktree removes the replaced CFFI
package and standalone Tools paths. Their disposition and remaining
consumer qualification are recorded below.

* Removal and custody policy

The user's target removes the obsolete Python framework/Tools paths, not their
useful contracts or negative verification obligations. Identify each consumer,
the replacement owner and evidence before removal. Move proof assets to =dev/=
without rewriting historical SHA-bound receipt payloads. Source-controlled
references used by current gates migrate; historical receipts retain their
original provenance and may carry an explicit relocation note.

No fallback aliases, temporary SDK, new load-path precedence, silent warmup,
foreign-memory cleanup omission or forced successful exit is acceptable. Rust
must consume the qualified existing Scheme/Rust mechanism rather than invent
another Scheme interpreter. Durable-storage and capability transport choices
need explicit reviewed contracts before implementation claims are made.
