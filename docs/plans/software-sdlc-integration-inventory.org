* Purpose

Lambda Aitia owns causal assurance for software engineering and the SDLC,
including the migrated SDLC, NASA and GitOps source modules.  It does not own
unrelated vertical business-domain models.  Lambda Episteme retains those
verticals, including Healthcare, plus independently owned decision-kind and
ontology surfaces.

The software Architecture Decision Record module is also Aitia-owned and is
published as =ADR=.  No lowercase compatibility module is retained.

The Aitia-side source migration and parity inventory are complete.  The
Episteme deletion is published, and the POO Flow main gitlink already pins a
clean Episteme cut.  The Aitia PR head is newer than the POO Flow main gitlink
and requires a separate pin update after acceptance.  This inventory governs
the post-migration boundary and prevents either repository from reintroducing
compatibility aliases or duplicate semantic owners.

Classification:

- =keep=: current owner remains authoritative;
- =reference=: Aitia consumes a public contract without copying it;
- =generalize=: implement a domain-neutral Aitia reasoning concept from the
  observed behavior, using new source and tests;
- =migrate-later=: move only after parity, ownership and dependency gates pass.

Lambda Episteme composes beside Aitia when an application needs non-SDLC
vertical knowledge; it is not an upstream owner for Aitia's SDLC semantics.
POO Flow execution does not redefine Aitia reasoning.

The complete SDLC organizes requirements, design, algorithm/implementation
strategies, testing, delivery, operation and evolution. RFC 0004 specifies how
behavior and design/assurance trajectories connect these activities. The
eight-step assurance/execution protocol is one mechanism within this framework.

* Existing semantics to preserve

The current SDLC implementation already enforces boundaries Aitia must not
weaken:

1. Project, evidence and review facts bind subject, revision and scope.
2. Evidence for another revision is classified as stale rather than current.
3. A review packet reports =compliance: not-evaluated= and
   =authority: not-verified=.
4. SDLC change impact returns deterministic witnesses and required verification
   rechecks but keeps =release-authorized? = false= and
   =runtime-executed? = false=.
5. NASA verification requests and lifecycle gates remain standard-specific and
   source-bound.
6. GitOps change, check and decision values preserve exact repository revision.

* First parity fixture

The first fixture is purely software engineering:

#+begin_export mermaid
flowchart TD
    R["Requirement R@1<br/>scoped"] -->|constrains| I["Implementation I@1<br/>candidate"]
    I --> V["Verification V@1<br/>checks I@1 against R@1"]
    V -->|bound admission| E["Evidence E@1<br/>current"]
    E --> O["Obligation O@1<br/>discharged for ReleaseClaim C@1"]
    O --> D["Decision D@1<br/>current under Snapshot G@1"]
    D --> X["Deployment Effect X<br/>requires separate authorization / Runtime gate"]
    C["R@2 or I@2<br/>changed"] --> A["Dependent assumptions and C@1<br/>impacted"]
    A --> S["E@1<br/>stale for changed closure"]
    S --> N["O@2<br/>pending for impacted verification set"]
    S --> B["D@1 invalid<br/>X blocked"]
#+end_export

Required negative cases:

- =implements= or =precedes= cannot by itself discharge O;
- a path containing an untyped edge is rejected;
- missing requirement-to-implementation traceability produces unknown;
- a proposed or counterfactual change cannot become committed history;
- E with a different repository/source digest is stale;
- an SDLC review packet or planner receipt cannot stand in for E;
- D does not prove deployment X started or completed;
- a NASA applicability decision cannot be generalized into a global Aitia rule.

* Post-migration integration sequence

1. Freeze the software fixture and negative contracts in Aitia.
2. Implement relation-plane and status vocabulary without importing a concrete
   standard, provider or vertical domain.
3. Implement snapshot and invalidation semantics with the POO Flow Graph
   library and reuse its impact, trajectory and SCC algorithms.
4. Preserve the completed SDLC/GitOps ownership cutover with source-collection
   and negative namespace tests.
5. Commit Aitia first, Episteme deletion second and parent gitlink/registry
   cutover last.
6. Extend the already landed AOT/CFFI transport beyond GitOps only after each
   corresponding Scheme semantic contract and negative matrix closes.

* Evidence required for migration acceptance

- source and target test inventories;
- exact public API diff;
- cold and warm build receipts for both repositories;
- deterministic canonical-output comparison;
- negative-contract parity;
- standard/proof/model dependency audit;
- POO Flow core bootstrap proving it does not import Lambda Aitia;
- application integration test showing stale software evidence blocks release
  and deployment effects;
- rollback plan retaining the original source owner until acceptance.

No item in this document authorizes moving SDLC, GitOps or Aitia Python
semantics back into Lambda Episteme or POO Flow's generic Python runtime.
