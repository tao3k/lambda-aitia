* Problem Statement & Research Lineage

RFC 0015 added RFC 6962 binary SHA-256 Merkle *inclusion proofs* proving that a single
repository link resides in a signed release attestation tree. In long-lived multi-repo
release trains audited by multiple independent consumers (Certificate Transparency
RFC 6962 §2.1.2 / RFC 9162 / Sigstore Rekor / Trillian), inclusion proofs alone do not
prevent a compromised log operator from presenting *split-view equivocation* (rewriting
an earlier epoch's entry while continuing to produce valid inclusion proofs against a
divergent root).

*Consistency Proofs* solve anti-equivocation logarithmically: given an earlier trusted
checkpoint ~(M, R_M)~ and a newer checkpoint ~(N, R_N)~ (~1 <= M <= N~), a consistency
proof of ~O(log N)~ hashes cryptographically proves that the first ~M~ entries of log
~T_N~ are bit-for-bit identical to ~T_M~ (strict append-only extension with zero
historical rewrite or truncation).

* Architectural Invariants

1. *Canonical RFC 6962 Merkle Tree Hash (MTH)*:
   - Single leaf: ~MTH(D[0..1]) = sha256(0x00 || canonical_json(D[0]))~
   - Recursive split at largest power of 2 strictly less than ~n~ (~k < n <= 2k~):
     ~MTH(D[0..n]) = sha256(0x01 || MTH(D[0..k]) || '|' || MTH(D[k..n]))~
2. *Strict Append-Only Consistency (RFC 6962 §2.1.2)*:
   - Rejects ~first == 0~ or ~first > second~ (anti-truncation).
   - Verifier independently reconstructs BOTH ~recomputedFirst == expectedFirstRoot~
     AND ~recomputedSecond == expectedSecondRoot~ from the exact ~O(log N)~ proof
     sequence (rejecting truncated, padded, or equivocated proofs).
3. *Zero-Unsafe In-Process Wheel Exposure & Zero Authority*:
   - Exposed directly on the ~#![forbid(unsafe_code)]~ PyO3 Python wheel
     (~generate_consistency_proof~, ~verify_consistency_proof~) with zero Scheme boot
     and ~actionAuthorized: false~ across every proof and verdict.
