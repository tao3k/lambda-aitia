* Receiver and loading ownership

The package Prelude already supplies =yuanxu!=. Product =init.ss= therefore
declares its selection directly, without importing the selection implementation
again. Relative role imports describe Scheme dependencies; the Module System
owns role resolution and its source/currentness guards. No business role
constructs a runtime import path or repeats a binding name in a delayed-loader
wrapper.

The GitHub Feature derives from its supplied receiver. Its nested =change=
operation reads the constructor from the final outer =self= when invoked.
It neither imports another constructor from the owner nor captures an eagerly
extracted parent procedure. A warmed parent adapter and an overridden child
therefore retain distinct receiver behavior.

POO =self= is the effective receiver. =sup= is the inherited computation for
the current slot, not the containing directory or the whole Module tree.
The inspected Haumea source at =252218e686de786f45311c323e105bd4340c2179=
supplies the current file result as =self=, the containing directory view as
=super=, and the perspective-dependent collection view as =root=. These
spatial capabilities are distinct from POO's inherited-slot continuation.
Consumers reach the selected tree through ordinary =init.exports= and =.get=:

#+begin_src scheme
(.get lambda-aitia.init.exports modules gitops)
#+end_src

Within a Module, cross-Module dependencies retain their declared =requires=
aliases. A namespace path or inherited slot does not create a dependency or
grant authorization. The structural namespace, receiver inheritance and
runtime import lifecycle remain distinct responsibilities.
