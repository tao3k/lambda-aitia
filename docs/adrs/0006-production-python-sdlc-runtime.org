* Context and Problem Statement

Lambda Aitia needs a Python runtime for downstream production systems.  A
binding presented as an example, or a Python implementation that duplicates
Scheme lifecycle semantics, would make ownership ambiguous and allow the two
implementations to drift.

* Decision

=bindings/python= is Lambda Aitia's production Python Runtime serving all its
capabilities within the complete SDLC: requirements, design, algorithms and
implementation strategies, testing, delivery, operation and evolution. Its
first lifecycle-planning API projects this assurance/execution protocol:

#+begin_export mermaid
flowchart TD
    C["change<br/>identified"] --> I["invalidate<br/>dependent support stale"]
    I --> P["plan<br/>obligations pending"]
    P --> V["verify<br/>candidate results produced"]
    V --> A["admit<br/>evidence accepted within scope"]
    A --> D["decide<br/>decision current"]
    D --> U["authorize<br/>bounded effect permitted"]
    U --> E["effect<br/>execution receipt recorded"]
    V -->|failed or unresolved| P
    A -->|relevant premise changes| I
    U -->|revoked or expired| I
#+end_export

Node labels describe the states a completed stage would establish. Feedback
edges describe lifecycle reassessment, not edges returned by the current API.
The API projects only an inert, ordered eight-stage DAG, not executed
transitions. Admission, decision, authorization and execution each require
their own checked receipt.

The responsibilities remain layered:

- Lambda Aitia Scheme owns SDLC stages, assurance semantics, decisions and
  attributable receipts.
- POO Flow owns reusable Graph/DAG algorithms and generic runtime mechanisms.
- The stable C ABI transfers owned JSON request and receipt bytes.
- Python validates and materializes those receipts for production consumers;
  it does not reproduce the semantic algorithms.
- AnyIO is the runtime-wide asynchronous foundation for structured task
  lifetimes, cancellation and bounded concurrency across Aitia capabilities.
  It does not grant Host authority or make an inert plan executable.

The first exposed planning operation is =SdlcRuntime.plan()=. It obtains the
eight-stage assurance DAG from Scheme through ABI revision 2. The plan is
inert and explicitly reports that it neither authorizes release nor proves
runtime execution.

* Consequences

- Downstream users depend on =lambda-aitia= as a real uv-managed project.
- Python API stability is a release concern, not example-code maintenance.
- No stage may be presented as executed until its Scheme operation publishes a
  source-bound receipt and the POO Flow runtime actually executes it.
- The full SDLC organizes the Python project; the planning API is one capability
  within it. Executable capabilities are delivered only with owned operations
  and attributable receipts.
- Generic temporal/causal trajectories and execution mechanisms are reused
  from POO Flow. Upstream tools, checkers and assets are qualified at their
  usable boundaries; MRR integration is deferred beyond this Python stage.

* Confirmation

- Scheme tests prove stage order, owner fields and inert authority fields.
- The pure-C harness resolves and calls the SDLC planning symbol.
- Python tests construct the typed plan through the bundled native library.
- Wheel verification imports and calls the installed production package
  without a Gerbil runtime in the Python process.

* Scope clarification

Revision r3 clarifies that the complete SDLC is the framework and the existing
eight-stage plan is its assurance/execution protocol. It preserves the Python
project and dependency ownership decision. Async execution, connected causal
trajectories and real tool-to-Host admission remain pending gates under
[[file:../rfcs/0004-sdlc-design-and-causal-trajectories.org][RFC 0004]].
