#+title: AITIA Rust Framework

* Implementation boundary

This directory owns the Rust implementation of AITIA's engineering framework,
not DE's Rust engineering Case. The same framework serves Rust, Python and
mixed-language user Projects. [[file:../docs/rfcs/0006-engineering-runtime-and-library-boundaries.org][RFC 0006]] owns its semantics and authority boundary;
[[file:../docs/plans/yuanxu-rust-framework-implementation.org][the implementation plan]] records unfinished work and acceptance controls.

Scheme/POO already owns the declarative language and Module composition. Rust
directly consumes it through =gerbil-scheme-rust=; it does not acquire another
Project/engineering DSL. The experimental handwritten Rust declaration types
were removed before acceptance because they duplicated that responsibility.
Module refinement, object identity and source authority remain with their
existing owners. Runtime effects remain explicit.
No handwritten generic graph, POO interpreter, policy evaluator, receipt issuer
or alternate package/source loader is part of this directory's mandate.

* Bridge and Module correspondence

Yuanxu's =yuanxu!=, Interface declarations and generated build projection own
module source association and configured scopes. Rust consumes a qualified
projection through the existing Scheme/Rust bridge. Actual Scheme object
identity, GC roots, owner-thread affinity and resource lifetime remain enforced
by that bridge; serialized identity strings are not authority capabilities.

The Rust archive contract requires the Orgize Elements values module and
the Orgize Contract values and evaluation modules exactly once. These
identities follow the Orgize revision pinned by Lab. The earlier archive
qualified against the prior interfaces remains a separate receipt.

With the Lab-pinned package set, fresh staging produced the new Orgize
module identities. The first linked gate reached the 120-second limit
after 101 seconds of compilation and linking. A subsequent run also
timed out. A diagnostic run against the newly staged archive completed
the Session and CLI checks in 31.28 seconds of test execution, including
normal shutdown. A subsequent full delivery run staged the program again
and passed linked integration in 37.37 seconds of test execution. Maturin
built the macOS arm64 ABI3 wheel, and the installed consumer passed Graph,
GitOps, ORG Contract, ORG edit preflight, and frozen pytest checks with
the same package set. The earlier cold timeout still applies to cold
build qualification.

The bridge currently has rooted Scheme-value and owner-lifecycle APIs. Its
historical VM-free Scheme-to-Rust subset compiler was removed upstream. Do not
design AITIA against that removed route or implement a replacement interpreter.
The precise bridge revision, public API, generated program and portable build
cohort must be qualified before adding a Cargo dependency or claiming execution.
The local upstream checkout alone is not a distributable dependency identity.

* Cargo workspace and development policy

=rust/Cargo.toml= is a virtual workspace, not one monolithic package.
=crates/aitia-runtime= owns actual Scheme program execution under the bridge's
Runtime lifetime. =build-support/aitia-build-support= owns shared ASP Rust
development policy. Further crates require real responsibilities and qualified
consumers; this design does not add empty placeholder packages.

The workspace pins bridge PR18 to =380f8ba5f87b2f9ba3924302b35b3eea1e3f2a8e=
and ASP Rust to =1ca41124b846dec947f3d05119cafa07eaa57924=. The production
member consumes Build Support only through =[dev-dependencies]=; ASP's own
documented Build Support pattern keeps its policy provider outside the Runtime
dependency graph. Cargo test invokes the upstream deny-mode workspace gate;
the local code does not implement another style scanner or suppress findings.
The Cargo lockfile is generated by Cargo. These Rust pins do not requalify
Lab's older Scheme package cohort or silently replace its manifests.

With the pinned bridge Scheme package compiled in the active package pool,
=just stage-rust-program= stages the compiler-generated AITIA program under
=GERBIL_PATH/native/aitia-program=. The program entry loads the Gerbil
expander through the SDK, and exports the SDLC flow graph and GitOps operations
using the bridge's rooted-call boundary. The compiler produces the builtin
Module list and startup stub. Archive linking, the Rust invocation and
installed-runtime qualification are separate gates. Run
=just test-rust-linked-program= to stage and link the graph and exercise the
published SDLC flow graph and GitOps decision. It supplies the SDK location reported by the paired
Gerbil executable. The Rust callback borrows the live bridge owner, so a
request or response root cannot outlive that owner.

Both bindings use the Scheme JSON projection in =bindings/operations.ss=.
Rust staging builds the selected Yuanxu UI closure and the linked program.
The archive contract rejects the legacy C transport and its ABI descriptor
module.

* Command-line consumer

=just build-rust-cli= builds =rust/target/debug/aitia= in the current package
pool. The Scheme-backed commands consume one UTF-8 JSON request from standard input and
return one JSON response on standard output. Invalid input and runtime
failures return a nonzero exit status.

#+begin_src sh
export GERBIL_HOME="$(gxi -e '(displayln (gerbil-home))')"
printf '%s\n' '{"lifecycle-id":"release/42"}' | rust/target/debug/aitia flow-graph
rust/target/debug/aitia gitops-evaluate < change.json
rust/target/debug/aitia org-contract-evaluate < elements-query.json
rust/target/debug/aitia jj-observe "$(command -v jj)" "$PWD"
#+end_src

The graph response contains the Scheme Graph's nodes and edges. The ORG
command uses the same Element request and verdict as the Python Session. A
valid query returns a verdict even if its expectation fails. Graph, policy
and ORG verdicts carry no effect authority.

The linked integration test exercises an ORG match through the CLI and
checks a failed expectation and malformed input through the same linked
program in one Session. This passed locally with an already staged
Scheme program. Fresh staging and installed-wheel acceptance with the
Lab-pinned package set remain separate gates.
The Scheme-backed commands use the installed Gerbil SDK and workspace
package pool. The read-only =jj-observe= command uses the supplied JJ
executable and returns the workspace cut directly through =aitia-jj=.
It does not initialize a Scheme session or issue write authority.
The linked Rust integration gate passed. A separate CLI run against JJ
=v0.47.1= in a disposable repository, with the Gerbil environment unset,
returned byte-identical cuts before and after creating an untracked file.
An explicit rewrite retained the change and parent identities and changed
the operation, commit and tree identities.

* Python distribution

The Python distribution is a Rust extension built with PyO3 and packaged
by Maturin. It consumes the Rust runtime and its Scheme bridge.
=just check-rust-delivery= qualifies the linked program and installs the wheel
built by that run in a fresh environment. Both checks use one staging of
the Scheme program.

The default Cargo workspace checks cover Rust code without starting or
building a standalone Scheme runtime. Only =linked-program= enables the
bridge, and the delivery gate exercises that feature through AITIA's
staged program.

The CI job installs the immutable Gerbil release through Lab's release
installer and resolves the Lab and Core package manifests through Lab's
Gerbil dependency entrypoint. It builds those producers before staging the
AITIA program. The wheel test uses the same Gerbil release and package
products as the linked Rust test.

=AitiaSession= owns one linked runtime thread for callers that need to
reuse it across requests. Its synchronous rendezvous keeps the request
queue bounded. Callers exchange owned Rust strings, and =close= joins
the owner after the bridge's cleanup. The linked Gerbil program is
one-shot within a process. A closed session cannot be reopened there.
The linked integration test exercises Graph consumption from another Rust
thread, invalid input, both GitOps verdicts, and explicit owner shutdown.

=just build-rust-wheel= builds the PyO3 extension with Maturin. Put
Maturin and a =pkg-config= implementation supporting =--keep-system-libs=
on =PATH= before staging. The bridge uses that option to retain system
linker arguments. The initial
development distribution is =lambda-aitia-rust= so it can be qualified
alongside the existing wheel. A fresh external virtual environment imported
the development wheel, read a Graph from another Python thread, received a
GitOps refusal and rejected a request after close. The repaired macOS 26
wheel was built separately. The smoke test uses the workspace Scheme package
pool and paired SDK. Orgize parity and an independently provisioned runtime
remain open.

On macOS 26.6.1 arm64 with Python 3.13.12, both existing wheels
installed and imported. With the workspace package pool but without an
explicit =GERBIL_HOME=, session setup returned
=GERBIL_STATUS_RUNTIME_UNAVAILABLE=. The repaired macOS 26 wheel read a
Graph and exited normally in a fresh external environment with the same
package pool and the paired =GERBIL_HOME= supplied. Use
=just check-installed-rust-wheel <wheel>= to verify the installed Graph,
GitOps decisions and session close under that runtime contract. A fresh release build with
Maturin 1.16.0 and pkgconf emitted the =macosx_14_0_arm64= wheel. The
installed check passed for that artifact and for the earlier
=macosx_26_0_arm64= artifact on macOS 26.6.1. The wheel tags identify the
artifacts tested. The fresh release wheel also returned an accepted
development decision for a current NASA source lock, then rejected a stale
lock for the same change. Neither response granted release or executed the
runtime effect.

=Session.org_contract_evaluate= takes a JSON request with =rows=,
=scopeId=, =queryKind=, =fieldName=, =fieldValue=, =expectation= and
=expectedCount=. Each row supplies =id=, =parentId=, =kind=, =fieldName=
and =fieldValue=. Parent =-1= denotes the root. An empty query field
selects by element kind. The response contains =matchedCount= and =passed=.
A valid query with zero matches returns an ordinary verdict. Invalid
inputs propagate as Session errors. The operation evaluates supplied
Elements and leaves source admission and authorization to their owners.
The Scheme transport test and fresh installed-wheel run passed. The wheel
checked field and kind matches, a missing field value, the three count
operators, malformed requests and continued use of the same Session
after a rejection. The existing Scheme binding and GitOps integration
suites also passed through =just test-integration= after the shared
projection changed.

Rust source capture preserves the =lambda-aitia.source-tree.v1= byte
format and the 64 MiB and 10,000-file limits. It walks relative to opened
directory handles and refuses symlinks and non-regular entries. It also
refuses path spellings that the Rust decoder cannot represent. The
decoder validates the file and byte limits, ordering, path safety, and
file-directory conflicts before returning borrowed file entries. The Rust
wire-order, round-trip, and malformed-input tests passed. =FrozenWorkspace=
prepares an isolated source directory from the validated bytes and owns
its cleanup. The workspace test confirms that editing either copy leaves
the other intact and that replay mutations are visible in a new capture. A fresh Maturin wheel passed the
same byte-format and directory-symlink checks through
=capture_source_tree(Path(...))= in an external Python environment.
The installed run also retained the Session, SDLC, GitOps and ORG controls.

=run_frozen_pytest= runs explicit selectors from a private frozen workspace
on Unix. It requires a caller-selected absolute Python interpreter and
uses a 30-second process deadline, an 8 MiB output budget and an 8 KiB
diagnostic tail. It reports the process outcome and whether a new capture
matches the original input. A bounded JUnit report supplies a SHA-256 digest
and observed pass, fail and skip counts. Malformed or unavailable reports
yield no counts. The focused real-pytest test covers successful execution,
report extraction, source mutation and invalid selectors.

The installed extension exposes =run_frozen_pytest(interpreter, payload,
selectors)=. Its result contains the process outcome, local verdict, exit code, source
comparison, the original and observed source SHA-256 digests, the selected
test names, diagnostic bytes and optional report. An unavailable recapture
has no observed digest. A local pass requires unchanged source, successful
exit, at least one passing case, and zero failed or skipped cases. Host
admission remains a separate decision. Set
=AITIA_PYTEST_PYTHON= to the absolute path of a Python interpreter with
pytest when running =just check-installed-rust-wheel <wheel>= to exercise
execution with a separate verifier environment.

=OrgEditReview::prepare= checks caller-supplied ORG projection spans
against the exact source bytes. It rejects stale digests, duplicate IDs,
overlapping ranges and edits that split UTF-8. The result holds ordered
edits and can recheck the source bytes before review. Orgize owns the
projection, and the review carries no write authority.

The Python wheel exposes the same check through =OrgEdit= and
=OrgEditReview(source_id, source, projected_sha256, edits)=. The source
owner supplies the bytes again to =source_current(source)=.

Independent SDK provisioning, trusted projection custody, and Host
admission of pytest observations remain open.

* Rust performance evidence

Measure cold process startup through the first Graph separately from steady
state calls on a live owner. In steady state, distinguish Yuanxu Scope
resolution and Graph construction from response projection, root transfer,
and output encoding. Keep execution and cleanup measurements separate when
the DE engineering drivers are attached. For Python, measure the PyO3
boundary against the same Rust operation and workload.

The linked tests currently establish behavior in the workspace pool.
Throughput, allocation and tail latency require release-build measurements
with a fixed Graph workload and a qualified installed consumer.

* Required framework consumer cases

| Framework use | Engineering selection | Evidence subject |
|---------------+-----------------------+------------------|
| Rust service development | applicable DE Rust concurrency/ownership plus independent design/release constraints | user's source and toolchain, not AITIA's own executor |
| Python framework development | applicable or newly contributed Python task/cleanup/compatibility definitions | user's Python environment and source, not AITIA's former Python bindings |
| AITIA self-engineering | applicable DE definitions bound to its Rust executor | AITIA implementation and bridge/runtime cohort |

Language selection is extensible, not a hard-coded two-language enum. Methods
and exploration branches are project-selected values, not a fixed next-action
pipeline. Tool observations, support admission, Human decisions and effect grants
must retain their independent issuers and currentness checks.

* Current qualification state

Workspace source and the first owner-scoped bridge call boundary are present.
AITIA AOT program projection, Module consumer parity, real process lifecycle
and recovery remain unqualified. A declaration-only five-test experiment is
withdrawn, not retained as evidence of the framework. Development proofs live in
=../dev/proof/= and consume the semantic Module owners.
